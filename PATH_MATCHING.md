# Path Matching Implementation

A key feature of BpfJailer is to be able to flexibly specify path patterns to allow/deny access to. This is applied to a variety of filesystem related system calls. Each node (file or dir) in a path is matched against a glob pattern that advances a state machine. Based on the results of the state machine a decision is made to allow/deny. Longest path (in terms of number of nodes) wins and is the one evaluated for policy. By default a path pattern is recursive and applies to any subdirectory/file.

All path matching is done against the root (pid 1) mount namespace. This is to create consistency in reasoning about paths and block unpriveledged mounting attacks. Any process can create a user + mount namespace which allows non-root users to create most non-device backed filesystems. The most destructive of these is a bind mount. Bind mounts create alternate paths that naive algorithms will follow breaking all path matching logic. BpfJailer ignores bind mounts where possible, even in the root ns, prefering to walk to a dentry/filesystem root rather then follow intermediate mount paths (more on that later). Eventually matching in arbitrary mount namespaces will be enabled, the algorithm can be extended to that easily, it just added complexity to the initial implementation.

## Glob Syntax

The globbing algorithm is currently simple. There is a lot of work queued up around extending it with more features (such as character sets) and optimizing it. It supports variables which are dynamic policy items set during pod creation that are unique to a pod. This allows a pod creator to fine tune the paths that can be matched. An example is a path like /run/containers/${ID}/root. ${ID} is replaced at match time by whatever the variable was set to during creation. Variables are immutable after pod creation. The point of this is to prevent cross talk between pods with the same role. In the example, two containers with different ${ID} variables cannot access eachother's directories.

The supported options currently are:
- ${} = variable definition. All allowed variable names are set in the policy file.
- * = match any set of characters.
- ? = match any one character.
- Literal characters

Again this will be extended over time.

## Dentries and Mounts

The Linux Virtual File System (VFS) is constructed from a mount tree. This tree can be different for each mount namespace. Mount namespace propogation rules are complex and out of scope here since we will focus on matching just in a single mount namespace. Each filesystem (not mount, filesystem), contains a tree of dentries, the nodes that comprimise the actual directories and files. These dentry trees are created lazily for filesystems backed by storage, they can be reaped if not used. For eBPF purposes we can assume they are always there for any path we are walking since the kernel won't reap dentries that point to the dentry we hold in an LSM hook. Dentries point to an inode which is the actual file/directory entry in the filesystem. Multiple dentries can point to an inode which is how hard links are implemented. The kernel doesn't distinguish between hard links, they are all identical to each other. It also doesn't track which dentries point to an inode in a reversible way. You can go dentry -> inode, not the reverse. Symlinks are resolved by the kernel before you are passed a dentry/path/file in an LSM hook. They are special inodes that point to a path, you never need to worry about them when path walking, the kernel passes you the "real" path (we'll soon learn that is somewhat a false conception).

Each struct mount has a mountpoint and a root. The mountpoint is the dentry it is mounted to in the a dentry tree. It could be in a different filesystem or the same one. This is how the VFS is constructed from a set of different mounts. All the dentry trees are isolated from each other but the mounts connect them. The root dentry is the starting point for that mount's dentry tree or subtree if it fully encapsulated within another filesytem.

The way the kernel walks a path is that it starts with a root mount and dentry. For each component in a path it checks the children of the dentry for matching names and moves into them. If a dentry is tagged as being a mount point, it consults the children of the mount it is holding onto. Mounts can be stacked (if you mount to the same mountpoint repeatedly), so the kernel follows newest at that location and only follows that mount. It ignores the ones underneath.

For example, let's open the file /tmp/foo. The kernel starts with the root mount and the root dentry names "/" (yes the only dentry that can have a slash in the name, don't ask me why). It then looks at the children of "/" for name "tmp." Once it finds that dentry it sees that it is a mount point and finds a tmpfs mount at that location. It moves to that mountpoint's root. Then it looks for "foo." Once found it moves to the "foo" dentry it stops and creates a struct file object. Importantly the struct path it preserves is the tmpfs mount and "foo" dentry. The recorded mount depends on how the kernel walked the VFS. This walking algorithm is highly optimized for this type of walk and is very efficient for walking down these trees.

But in LSM hooks we don't walk down the tree. For path matching we generally walk up. We are passed a dentry (and sometimes a mount). We need to do this operation in reverse. The kernel does have all the information needed to do that.

Most filesystems construct a new dentry tree, and when mounted create a mount pointing to the root of that tree, but not all follow that pattern. In fact mounts can point to non-root nodes in a filesystem's tree. But wait? How can one mount be in another mount's dentry tree? Bind mounts (and overlayfs sort of) are the answer. A bind mount is not a symlink, or a hard link, though it is common to think of them as one of those. It is a full mount copy, mounted into another mount's dentry tree that points (root dentry) somewhere else. Almost anywhere else actually. Cross filesystems or within a filesystem. Importantly under a bind mount (though it points to the same dentry tree) you won't link back to other places in the mount tree, the kernel makes a new leaf for the bind mount. However, if you specify the recursive option it duplicates (yes duplicates not links) all of the mounts underneath the chosen root.

For path matching bind mounts are an extremely serious problem, especially since any user can create them in a user + mount namespace (they don't propogate upwards but are valid paths). If I have /var/secret, I can make /evil/var/secret and then the path is different. In the LSM hooks there is no way to protect against this since the lsm/sb\_mount hook passes you the new bind mount root as a string, which needs to be parse and can contain symlinks, so you can't effectively stop evil bind mounts. In addition the inode LSM hooks don't provide you a struct mount to use. The "standard" way to walk the VFS is to have both a dentry and a struct mount. Each dentry links to a parent. When the dentry = mount-\>root, then you've hit the mount and you can walk more from the mount-\>mountpoint. The dentry tree never links to a mount, the mount tree links to the dentries. This is an extremely serious issue because if a path is opened through a bind mount you will walk that bind mount's path, and you will be a vitim of whatever path the attacker chooses to provide you. Again, they don't need root to do this, and many containers and namespace based jailers need unprivledged mounts to set themselves up, so it is not usually desireable to block this. Also bind mounts are everywhere and you don't want to track them down.

What we want is to throw out that mount argument and ignore it, and walk with only the dentry plus another data source that links the mounts together. This lets us choose the namespace and path through the mount tree that we choose. We want to always ignore bind mounts and overlayfs manipulation.

## Traversing the Mount Tree

Each struct mnt\_namespace contains an rb tree of all struct mounts it owns. As stated before, these mounts are linked to eachother in a tree that represents their structure, and each mount effectively links two dentries (which might be in different trees), root -> mountpoint. The kernel maintains two global locks the mount\_lock and rename\_lock. It bumps these on mount and rename operations. A mount operation aquires this lock. eBPF can't acquire those locks, but has to respect them. BpfJailer simply retries matching until the locks don't change underneath it during the operation. When walking, what we need is to traverse the mount tree but from leaf -> root, the opposite direction the kernel expects. The way we do this is to explore the rb tree that the namespace maintains. For each mount in the rb tree we connect the root dentry to the mountpoint of the containing mount to the mountpoint in a hashmap of dentry -> mount (which contains the mountpoint). This allows us to get a mapping of how all the dentry trees are connected, not just the path the kernel followed in opening. Importantly, the kernel maintains a unique counter that it assigns to every new mount and then bumps. This let's us determine the oldest mount at a mountpoint. This is vital. If a process creates junk such as bind mounts, overlays, tmpfs, over an existing valid mount we want to know about it and discard those new mounts.

What we wind up with the ability to map any dentry to the oldest mount containing it, something not normally possible because of the unidirectional flow the kernel follows. This let's us jump through the mounts in the order we think is valid. We follow these rules:
- Ignore mounts not at dentry roots or btrfs subvol roots. These are almost certainly bind mounts or other junk we don't care about.
- At a root jump to the oldest mount with that root and move to its mountpoint.
- Stop iteration at the namespace root dentry. If that can't be found (we end up at the tip of a dentry and there are no mounts to move up to), we fail open (usually). This was a concious decision since we currently only care about files resolvable in the root mount namespace. As stated later we will support matching in any targetted namespace. Usually these files are scoped to a specific container or jail anyway by mount namespace topology.

We match each dentry name against the set of globs we have configured and use it to advance a state machine. Each dentry node either advances an iter or drops of {pattern id, position in that pattern}. Any iters that survive to root are considered matched and we select the longest as the match.

This mount map is invalidated on changes to the root mount namespace, and we retry the walk if mount or rename lock change under us.
